# Phase 8: Desktop releases and package managers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the Backroom desktop app as GitHub Releases for Linux, Windows and macOS (with a Windows installer), and prepare it for installation through pacman/yay (AUR) and other package managers. Because Backroom is self-hosted, the released app must work with ANY server: it asks for the server address on first launch.

**Architecture:**
1. The Tauri shell stops depending on a build-time `BACKROOM_APP_URL`. On launch it reads a stored server address; with none, it shows a small bundled setup page that validates and saves one. The origin lock, the remote capability and the deep-link flow all follow the stored origin.
2. A release workflow builds every platform on tag push and uploads installers and checksums to a draft GitHub Release.
3. `packaging/` holds manifests (AUR, Homebrew cask, Scoop, winget) generated from the release checksums by one bump script.
4. README and docs describe installing on every platform.

**Tech Stack:** Tauri 2.12.5 (already pinned) with the existing plugins, GitHub Actions (`tauri-apps/tauri-action`, pinned by commit SHA), `makepkg` in an Arch container for the pacman package, plain manifests for the rest.

**Spec:** docs/superpowers/specs/2026-11-11-backroom-design.md §11 (updated in Task 1 for the runtime server address).

## Global Constraints

- Never push, tag or publish anything without the user's explicit go-ahead. Publishing to the AUR, Homebrew, Scoop, winget or any registry, creating a tag, creating a release, and pushing branches to GitHub are outward-facing: tasks prepare and verify locally only.
- Never log or store codes, verifiers, tokens or message bodies. Keep the existing desktop security model: origin lock, capability scoped to exactly the saved server origin and the main window, viewer windows without IPC, deep-link PKCE hand-off.
- The user's earlier rulings still bind (P5, P6, P7). Exact version pins; pin every third-party GitHub Action to a full commit SHA with a version comment, and use only versions at least 14 days old.
- Release builds are unsigned unless signing secrets exist: document the Windows SmartScreen and macOS Gatekeeper consequences honestly; do not add signing code that needs secrets this phase beyond optional, clearly documented environment hooks.
- No private information in committed files (no personal email, maintainer domains, IPs, account or resource IDs).
- The machine is low on memory: run one heavy command at a time (cargo builds, test suites).
- Commit messages end with a blank line and `Claude-Session: https://claude.ai/code/session_0163nEV5tSsJFQCKT3iMKfqb`.

## Review Focus

1. A stranger installs the released app, types their server's address once, signs in, and everything (notifications, tray, deep links, downloads, viewer windows) works with that server; typing a hostile address (`javascript:`, `file:`, an address with credentials, a path) is refused; changing the server later works and revokes the old origin's capability.
2. The release workflow cannot publish anything by accident (draft release only, runs only on tags or manual dispatch with a dry-run input), uses no secrets, and every action is SHA-pinned.
3. Manifests reference the exact asset names and checksums the workflow produces and nothing else.

### Task 1: Runtime server address in the desktop app

**Files:** `apps/desktop/src-tauri/src/{config.rs (new), lib.rs, commands.rs, policy.rs, tray.rs}`, `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/dist/` (the bundled setup page: `index.html`, a small script and style, no external resources), `apps/desktop/src-tauri/build.rs` (command manifest), capabilities, tests, spec §11, README desktop section (short).

- [ ] Stored configuration: `server.json` in the app config directory (mode 600/dir 700 on Unix) holding `{ "serverUrl": "<origin>" }`. Pure, unit-tested functions: `normalize_server_url(input) -> Result<Origin, ConfigError>` (trim; add `https://` when the scheme is missing for a hostname; accept `http://` only for `localhost`, `127.0.0.1`, `[::1]` and RFC 1918 / `.local` hosts with an in-app notice that traffic is not encrypted; reject credentials, paths other than `/`, query, fragment, non-http(s) schemes, empty hosts, overlong input; lowercase host; strip default ports), `load_config`, `save_config` (atomic write).
- [ ] Startup order: the build-time `BACKROOM_APP_URL` stays as an optional default (used by smoke tests and distro builds); precedence is stored config, then build-time default, then the setup page. When there is an origin, the main window loads it exactly as today (origin-locked navigation, runtime `remote-app` capability scoped to that origin, deep-link handling, notifications). When there is none, the main window loads the bundled setup page and NO remote capability is added.
- [ ] Setup page (`apps/desktop/dist/index.html`): one field, a Connect button, an inline error area, an explanation line ("Enter the address of your Backroom server, for example https://chat.example.com"), keyboard accessible, light/dark by `prefers-color-scheme`, no external fonts or scripts. It calls two commands through a LOCAL capability that applies only to the bundled page (window label `main` while on the app's own `tauri://` origin; not to remote origins): `check_server(url) -> {origin, insecure}` (normalise and, from Rust, GET `<origin>/health` with a short timeout, expecting HTTP 200 and JSON `{"ok":true}`; surface a clear error otherwise) and `save_server(url)` (re-validates in Rust, saves, then navigates the main window to the origin and adds the remote capability for that origin). Never trust the page's own validation.
- [ ] Changing the server: a tray menu item and an application menu item "Change server…" clears the stored config, removes the remote capability for the previous origin if the runtime API allows it (otherwise restarts the app window via the setup flow and documents that the capability dies with the process: prefer relaunching the app with `app.restart()` after clearing), and shows the setup page. Add the item to the tray menu; keep Show/Quit.
- [ ] ACL tests with the mock runtime (as in Phase 5/6): the setup commands are callable from the bundled page and NOT from a remote origin page; the existing remote commands stay callable only from the saved origin; a page on a different origin (the previous server, or another host) is denied after a change. A test that a hostile `serverUrl` in a hand-edited config file is rejected on load (falls back to the setup page) and never reaches the capability builder.
- [ ] Update spec §11 (runtime server address, precedence, setup page, "Change server", capability behaviour) and the README desktop section (short; Task 4 finishes docs).
- [ ] Run `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo build` (one at a time) and the web tests if the bridge changed. Commit `feat(desktop): choose the server address at runtime`.

### Task 2: Cross-platform bundle config and the release workflow

**Files:** `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/icons/` (add `icon.ico`, `icon.icns` generated from the existing source PNG with `npx tauri icon`), `apps/desktop/src-tauri/linux/`, `apps/desktop/package.json`, `.github/workflows/release.yml` (new), `scripts/set-version.mjs` (new), `docs/RELEASING.md` (new).

- [ ] Bundle targets: `deb`, `rpm`, `appimage` (Linux); `nsis` and `msi` (Windows); `dmg` and `app` (macOS). Windows: NSIS per-user install by default (no admin prompt), a Start Menu entry, WebView2 install via the downloaded bootstrapper (`webviewInstallMode: downloadBootstrapper`), the `backroom://` URL scheme registered by the installer (the deep-link plugin config; check the Tauri docs for NSIS/MSI scheme registration), license file from the repo's MIT LICENSE, language English. macOS: minimum system version per Tauri's default, bundle identifier unchanged (`app.backroom.desktop`), deep-link scheme in Info.plist through the plugin config. Linux: keep the custom `.desktop` template with `%u` and the MimeType.
- [ ] `scripts/set-version.mjs <x.y.z>`: validates semver and updates `apps/desktop/package.json`, `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/Cargo.toml` (+ the `Cargo.lock` package entry via a precise edit or `cargo update -p backroom-desktop --offline`), refusing to run on a dirty tree unless `--force`; prints the changed files. Test it with a temp copy of the files.
- [ ] `.github/workflows/release.yml`: triggers `push` of tags matching `v*.*.*` and `workflow_dispatch` with an input `dry_run` (default `true`); `permissions: contents: read` at the top, `contents: write` only on the job that creates the draft release; concurrency per ref. Matrix build jobs: `ubuntu-24.04` (deb, rpm, AppImage; install the Tauri Linux deps plus `rpm` and the AppImage prerequisites), `windows-latest` (nsis, msi), `macos-latest` (aarch64 dmg) and an Intel macOS runner (x86_64 dmg) or one universal build if `tauri-action` supports it reliably. Each job: checkout, Node from `.nvmrc`, Rust stable, `swatinem/rust-cache`, `npm ci`, then `tauri-apps/tauri-action` (SHA-pinned) with `tauriScript: npx tauri` in `apps/desktop`, uploading bundles as workflow artifacts (the desktop app bundles only its setup page, so no web build is needed). A final `release` job (needs: all builds, runs only for tag pushes, never for dry runs): downloads artifacts, computes `SHA256SUMS`, creates a DRAFT GitHub Release for the tag with the installers and `SHA256SUMS` attached, notes generated from the commit log since the previous tag. Asset names are stable and documented; verify the real names from a local Linux build and from the Tauri docs (expected: `Backroom_<version>_amd64.deb`, `Backroom-<version>-1.x86_64.rpm`, `Backroom_<version>_amd64.AppImage`, `Backroom_<version>_x64-setup.exe`, `Backroom_<version>_x64_en-US.msi`, `Backroom_<version>_aarch64.dmg`, `Backroom_<version>_x64.dmg`) and record the final list in `docs/RELEASING.md`.
- [ ] Leave a clearly marked placeholder for the Arch package job in the workflow; Task 3 adds it once the PKGBUILD exists.
- [ ] Validation: YAML parse; `actionlint` if available (try `npx --yes actionlint`, otherwise parse only); a local Linux build of the bundles (rpm only if `rpmbuild` exists); list the produced asset names and compare with the workflow's expectations; run `set-version.mjs` against a temp copy. All action SHAs come from `git ls-remote` tag lookups (annotated tags need the `^{}` line); versions at least 14 days old.
- [ ] `docs/RELEASING.md`: how to cut a release (set version, commit, tag, push the tag, review the draft release, publish), the dry run via workflow_dispatch, the asset names, what is unsigned and what users will see (Windows SmartScreen "More info → Run anyway", macOS "right-click → Open" or `xattr -dr com.apple.quarantine`), and how a maintainer could add signing later (secret names only, nothing implemented).
- [ ] Commit `ci: cross-platform release workflow, bundle config and version script`.

### Task 3: Package manager manifests

**Files:** `packaging/aur/backroom-bin/{PKGBUILD,.SRCINFO}`, `packaging/aur/backroom/{PKGBUILD,.SRCINFO}`, `packaging/homebrew/backroom.rb` (cask), `packaging/scoop/backroom.json`, `packaging/winget/*.yaml` (version, installer, locale manifests), `scripts/packaging-bump.mjs`, `packaging/README.md`, workflow additions.

- [ ] `backroom-bin` (AUR): installs the release `.deb`'s payload (extract with `bsdtar`/`ar`) or the AppImage; `depends` on `webkit2gtk-4.1`, `gtk3`, `libayatana-appindicator` (verify names from the deb's `Depends` and Arch package names), installs the desktop file, icons and the `backroom://` MimeType registration, license MIT; `source=` points at the GitHub release asset URL with `sha256sums` filled by the bump script; `provides=('backroom')`, `conflicts=('backroom')`. `.SRCINFO` generated by `makepkg --printsrcinfo` inside an Arch container if one can be run locally (otherwise generate it by the workflow job and document it). A second package `backroom` builds from the tagged source (`rust`, `nodejs`, `npm` as makedepends, `npm run build -w apps/desktop` with no bundling or the repo's build) with the same runtime deps. Namcap-clean where feasible.
- [ ] Homebrew cask (`brew install --cask backroom`, from a tap `homebrew-backroom` that the maintainer creates): url from the release dmg for the right architecture (`on_arm`/`on_intel`), sha256, `app "Backroom.app"`, `zap` stanza for the config directory, a `caveats` block about the unsigned app. Syntax check with Ruby if available.
- [ ] Scoop manifest (`scoop bucket add backroom <repo>`): version, the NSIS installer url and hash, `checkver` github, `autoupdate`. JSON-valid.
- [ ] winget manifests (three YAMLs in the standard layout): `PackageIdentifier`, installer type `nullsoft` for the NSIS exe (silent switch `/S`) with `InstallerSha256`, `Architecture: x64`, license MIT, publisher and URLs from the repo. Validate their structure with a small script against the documented required fields.
- [ ] `scripts/packaging-bump.mjs <version>`: reads the release's `SHA256SUMS` (a local file or a downloaded one), then rewrites version and checksums in every manifest above and prints a diff summary; `--check` mode verifies that every manifest already matches `SHA256SUMS`. Tests with a fake `SHA256SUMS`.
- [ ] Workflow: add the Arch job to `release.yml` (container build of both PKGBUILDs, `namcap`, upload `.pkg.tar.zst` assets to the draft release so `pacman -U` works), and a `packaging-check` job on pull requests that validates manifests syntactically without network (PKGBUILD via `bash -n`, JSON/YAML parse, cask via `ruby -c` if installed on the runner).
- [ ] `packaging/README.md`: for each manager, exactly what the maintainer does to publish (AUR: create the account, add an SSH key, clone the AUR repo, copy, push; Homebrew: create the tap repo and copy the cask; Scoop: create a bucket repo; winget: `wingetcreate` or a PR to microsoft/winget-pkgs), flagged as manual publication steps requiring the maintainer's accounts. Nothing is published by the repo's CI.
- [ ] Commit `feat(packaging): AUR, Homebrew, Scoop and winget manifests with a bump script`.
